# March 2026 – Incident Response & Security Operations

## Overview

In March 2026, I participated in an Incident Response sprint focused on detecting, analysing, and responding to security incidents within a simulated enterprise environment.

This phase built on previous threat intelligence and cloud security work by introducing real-world incident handling processes, including alert investigation, log correlation, and response decision-making.

The objective was to develop a structured approach to identifying security incidents, understanding attacker behaviour, and applying appropriate response actions within a SOC environment.

---

## Key Responsibilities

During this sprint, I contributed to the investigation and analysis of simulated security incidents.

My responsibilities included:

- Investigating security alerts and suspicious activity  
- Analysing logs from multiple data sources  
- Identifying indicators of compromise (IOCs)  
- Mapping observed behaviour to known attack techniques  
- Supporting incident response decision-making  
- Documenting findings in a structured and professional format  

This experience closely mirrored the responsibilities of a Tier 1 SOC Analyst.

---

## Incident Response Activities

### Alert Investigation & Triage

I worked with simulated alerts generated from security monitoring systems.

This involved:

- reviewing alert details and context  
- determining whether activity was benign or suspicious  
- prioritising alerts based on potential impact  

Key learning:

Not all alerts represent real threats — effective triage is critical in reducing false positives and focusing on genuine risks.

---

### Log Analysis & Correlation

To understand each incident, I analysed logs from different sources and correlated events.

This included:

- authentication logs  
- system activity logs  
- network-related events  

By correlating logs, I was able to reconstruct attacker activity and identify patterns that would not be visible from a single data source.

---

### Threat Detection & Behaviour Analysis

I analysed suspicious behaviour to determine whether it aligned with known attack techniques.

Examples of activity investigated included:

- unusual login patterns  
- suspicious command execution  
- abnormal system behaviour  

Key learning:

Detection is not just about tools — it requires understanding how attackers behave across different stages of an attack.

---

### MITRE ATT&CK Mapping

During investigations, I mapped observed activity to known MITRE ATT&CK techniques.

This helped to:

- understand attacker intent  
- classify the type of activity observed  
- align detection with recognised industry frameworks  

Key learning:

Using frameworks like MITRE ATT&CK improves consistency and clarity in threat analysis.

---

### Incident Timeline Reconstruction

I built timelines to understand how incidents developed over time.

This involved:

- identifying the initial point of compromise  
- tracking attacker actions step by step  
- determining the sequence of events  

Key learning:

Timeline reconstruction is essential for understanding the full scope of an incident.

---

### Response & Containment Decisions

Based on investigation findings, I evaluated appropriate response actions.

These included:

- isolating affected systems  
- recommending credential resets  
- suggesting further investigation steps  

Key learning:

Effective incident response requires both technical analysis and decision-making based on risk.

---

## Key Security Insights

Through this sprint, several important insights emerged:

- Many attacks follow predictable patterns that can be detected early  
- Log correlation is critical for accurate investigations  
- False positives are common and must be handled efficiently  
- Fast and structured response reduces potential impact  
- Understanding attacker behaviour improves detection capability
